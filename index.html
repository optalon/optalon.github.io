OpenTalon

Briefly on OpenTalon

OpenTalon is a game engine that runs Aliens versus Predator 2 from the game's data files natively on Linux and on 64-bit Windows.

This guide is for a person who is about to open the source tree and wanting to know where things are before doing so. We start with the cornerstone architectural objects, then go down to the classes doing the actual work. The story on the compatability with the legacy binaries and renderer are left to the last tab, for readers curious about that sort of thing.

Why two engines?

Because a dedicated server should not carry a renderer, and a client should not be able to peek into server state by accident. Also, if the client can reach the server's objects directly, sooner or later some code does, single player keeps working, and multiplayer breaks in a way hard to reproduce alone.

So there are three ways to arrange the same parts in a process.

What happens in a frame?

Here by "frame" we mean a game "step"/one iteration of a game cycle + renderer. At the moment, its equivalent to frames in FPS, although in the principle number of actual rendered frames and game logic steps need not to be dependent.

Each engine runs a frame in one function. Below are the steps of each in the order the code performs them. The third list follows one 3D scene from the client down to the swapchain.

          Wiring a renderer to the engine

          The renderer is the one part of OpenTalon designed to be replaced. The engine does not know what Vulkan is. It knows one struct, RenderStruct, which is 576 bytes long (0x240). It holds fifteen function pointers written by the engine, 38 written by the renderer, and a few dozen bytes of state read by both. Neither side needs to know anything else about the other.

          OpenTalon's renderer, talon.ren, is linked straight into the client and still goes in through the very same interface - and this page is about it.

          Offsets on this page are those of the 64-bit builds, Linux and Windows alike. The ones for RenderStruct were printed by a program compiled against the header. They are given for reading a memory dump. Code uses the field names in runtime/client/renderstruct.h and the accessors in renderobj.h.

          What's the contract between the engine and the renderer?

          One struct in four parts, declared in runtime/client/renderstruct.h. Click a part.

          The struct is a member of CRenderMgr and there is one of it. It is written at three moments.

          1. Engine start. The whole struct is zeroed, the fifteen callbacks are written, and the sun is given a default direction.
          2. Setting a video mode. Everything before m_DontClearMarker is zeroed (0x1e0 bytes) and the callbacks are written back. The renderer's setup function then fills the slots. The engine writes m_Width and m_Height and calls Init with a RenderStructInit: the wanted mode and the window handle go in, the mode actually set and the renderer's version number (3421) come out. On success m_bInitted becomes 1.
          3. Shutting the renderer down. After Term the same 0x1e0 bytes are zeroed and the callbacks written back. The last 0x60 bytes are left alone both times.

          A renderer is compiled into the client. It provides a setup function filling the struct, and CRenderMgr::SetRenderMode picks that function by the renderer's name. That is two lines for talon.ren and will be two more for a second renderer.

          Also, the struct is not quite the whole contract any more.           In what order will it be called?

          Over the life of a session, like this. Nothing here is per frame except the step saying so.

            And a frame?

            The game shell is in charge of a frame. It decides when the screen is cleared, when the 3D part begins, how many cameras are drawn and when the result is shown. The engine translates, and the renderer gets called. Click a row.

            A renderer may draw inside RenderScene, and the original renderer did. talon.ren does not. It copies the scene description, returns at once, and does all the building and all the drawing at the flip, because the graphics layer under it allows one pass to the swapchain per frame and a frame may hold several scenes. A renderer going the same way finds that anything it calls back into the game for (the model hook, above all) then runs at flip time and not where the game thinks it does.

            What is in a scene?

            A , 0x104 bytes. It is built fresh for every call, and it comes in two kinds. Click a field.

            What does an object look like?

            Like a block of memory at fixed offsets, with no class to go with it. The engine keeps its objects in its shape and, once a frame, writes a render block for each drawable one. Every block starts with the same 0x1b0 bytes. Click a field.

            What follows the head depends on the type byte.

            And the level?

            The level is handed over once, when it loads: CreateContext receives the address of a pointer to a WorldRT, and whatever the renderer builds from it (vertex buffers, lightmap atlases) is its context. The context is returned in every scene description, and the renderer is told when to delete it. Click a box.

            The original renderer asks the level questions through C++ virtual calls in a 32-bit calling convention, which is of no use on a 64-bit machine. So past the end of what the original ever reads, the world record carries the same answers as plain function pointers. We call them channels.

            Who owns the pixels?

            Textures
            The engine owns the files and the renderer owns what is on the GPU. Nothing is pushed to the renderer. When it meets a texture it has not seen, it asks for the data, uploads it, and tells the engine it may let go of its copy. What it receives is the file's image as it came out of the archive, still compressed: DXT1, 3 or 5, or plain 32-bit, with every mip level. Each texture record has one pointer reserved for the renderer, and it starts out null.
            Models
            The engine lays every model out once in a renderer-friendly shape: pieces, vertices with their bone weights, triangles. The pointers never move afterwards. Bones are the engine's business. The renderer asks an instance for its node transforms and gets them in model space, already animated and blended. Whether skinning then happens on the CPU or in a shader is left to the renderer; talon.ren does it in a shader with a palette of at most 96 nodes.
            The 2D layer
            All the engine's. Menus, the HUD, the console, videos: the game draws them into a plain 32-bit surface in the engine's memory, and the renderer never sees a blit. Once a frame the engine locks the renderer's screen buffer, copies in the changed parts, and unlocks it. The renderer's 2D work is to put that buffer over the 3D picture at presentation.

            What can the game do to the frame?

            None of the following goes through the renderer, and all of it changes what the renderer is expected to draw.

            Cameras
            A camera is an object with a rectangle, a field of view and a "light add" colour. The game draws one or several per frame, each as a separate scene. The light add is the screen flash: one colour, added over the finished scene.
            The model hook
            A function the game registers and the renderer calls once for every model, right before drawing it. It may change the model's colour, its added light and a few flags, for that one draw only.
            Global tints
            A light scale and a vertex tint for the whole scene, set by the game's camera code before each camera is drawn.
            Canvases
            An object made of nothing but a callback. The renderer calls it with a small drawing interface, and the game issues triangle fans into the renderer's frame from inside its draw loop.
            Console variables
            Fog, its colour and distances, full-bright, the far plane, detail switches. The game sets them as console variables, and the renderer re-reads them when the engine calls ReadConsoleVariables, which it does only between scenes.
            Object flags
            Visible, casts a shadow, ignores fog, ignores light, environment-mapped, additive, multiplied, chroma-keyed. Also "really close", which means the object's position is already in camera space.
            The sky
            The game shell does not set it. The server names the sky objects and the box the sky camera moves in, and the client engine passes them on in every scene description.

              How the server talks to its clients

              This page is about plumbing. What a datagram looks like, what happens when one is lost, at which point of a frame the server sends, how it decides who is told what and how bandwidth is governed. The game's protocol (and MSP protocol as well) are irrelavent here and not discussed.

              The short version: everything is UDP on one non-blocking socket, a datagram is at most 1,100 bytes, and there are two lanes on top of it. One lane delivers everything, in order, eventually. The other delivers the newest thing or nothing. Most of the work is in deciding what goes on which lane and how often.

              Numbers on this page are the defaults in the source as of October 2026. Almost every one of them is a console variable.

              What is on the wire?

              Bytes. The packet class writes whole bytes in little-endian order and has no notion of a bit. The later LithTech engines address packets by the bit, and reusing their reader here would mis-frame every packet. So where this engine saves space, it does so by choosing a narrower type for a field, and we will get to those.

              A datagram takes one of five shapes, and its first byte says which. Pick one and click a field.

              How does a client get in?

              With a handshake of two messages, a megabyte of file names and one burst of object creations. The steps are below. The third one is easy to get wrong, and we did.

                What if a datagram is lost?

                On the guaranteed lane every packet carries a number, and the sender keeps the packet until the other side says it has everything up to that number. There is no resend timer. The receiver drives recovery: it delivers packets strictly in order, holds whatever arrived early, and lists what is missing in its next ack, at most eight numbers at a time.

                Below are ten guaranteed packets in flight. Click one to lose it and see what the receiver does about it.

                The sender answers the first request for a packet at once and then waits one and a quarter round trips before answering the same request again. Answering every request would put one more copy per ack on a link dropping things at that moment.

                The last packet
                Nothing arrives after it, so the receiver has no way to notice it is gone. If the newest unacknowledged packet stays uncovered for one and a half round trips, the sender sends it once more unasked.
                Copies in advance
                A packet still unacknowledged after about 33 ms goes out a second time with the same number. After twenty seconds the server knows the link's pattern of losses and picks the delay per client, somewhere between 30 and 130 ms.
                An outage
                A full list of eight missing numbers is read as "the link was down for longer than I can say in one ack". Everything sent during the gap goes again at once, without waiting to be asked for eight at a time.
                The other lane
                An unguaranteed packet has no number. It is delivered when it arrives and forgotten if it does not. Positions travel this way, because the next one is already on its way.

                When does the server send?

                At the end of the frame, after the game has run. A server frame reads the network, lets the game and the physics do their work, and only then writes. The host steps the server at 100 Hz, but a client is not sent to on every step: each client has a pass, which comes around as often as that client asked for, between 2 and 60 times a second.

                  Sending 60 times a second on a 100 Hz step needs some thought. Below is one second of server steps, and the filled ones are those on which a client's pass falls.

                  Who is told what?

                  Every client has an array with one small word per object, and whenever anything about an object changes, the matching bit is set in the array of every client. Nothing is sent at that moment. When a client's pass comes, the server walks that client's array and writes the object's state as it is now. An object costs one record even if it changed forty times since the last pass, and the record is never stale.

                  The original engine stops here and sends every moving object to every client. With a hundred aliens on a level this came to 226 KB/s for a single client, so we added one thing: decides how often a client hears about an object.

                  The table follows the rate chosen in the previous section. A skipped object keeps its change bits, so the next record carries where it is by then and skipping costs latency only. When the server cannot tell (no PVS, a point inside solid) the answer is "near".

                  How bandwidth is governed?

                  By 2 governors! And the lower of the two wins.

                  The first is the original one. It counts how many of the server's sendto calls the operating system refused in the last frame and scales every client's rate down by that share. Perhaps this meant something on the links of 2001. On a real link today the kernel accepts every datagram and the network drops them a few hops later, so this governor sits at 60 while 41.6% of what the server sends is lost and a guaranteed message takes half a minute to arrive. We measured that before writing the second one.

                  The second is OpenTalon's and works per client. It watches that client's connection for two signs of a full pipe: acks coming back later than the best they have recently been, and guaranteed packets needing to be asked for again. Either one, sustained, is a verdict. The buttons below show what a verdict does to the ceiling.

                  When things are worse than slow, there is a third measure. If the oldest unacknowledged guaranteed packet is more than 150 ms older than it ought to be, the pass is shed: the client is told where it is itself, what time it is, and about everything near it at full rate. Only the far objects wait.

                  What about the game's messages?

                  The game module calls SendToClient and believes the message is gone, but the engine only copies it into that client's queue and puts it on the wire on the client's next pass, after the object records, since a message mentioning an object had better arrive after the object does. Of the flags the game may pass, the engine reads one, whether the message is guaranteed.

                  A message is its data followed by its id, in that order, so the id is the last byte. It must fit in one datagram, which leaves 1,098 bytes. A longer one is refused with a line in the log and is not split.

                  How do I see any of this?

                  By asking the server to print it, or by putting a bad link under it on purpose. Everything here exists because at some point we could not tell what was going on.

                  Driving a server from outside

                  A running server can be watched and driven by a program sitting next to it. We call such a program a controller. It connects over TCP, asks questions (who is playing, where are the bots, can a Runner get from here to there) and gives orders (spawn this, move that, say something in chat). The xenomorph hive on a co-op server, the sentry guns players install, the APC falling out of the sky are all controllers, and none of them is compiled into the engine.

                  The web panel in a browser goes through the same command table, so the panel can do nothing a controller cannot, and anything a controller does is visible in the panel.

                  The first half of this page explains the mechanism and the API. The second half builds two controllers step by step, the Xeno Director and the APC, with code taken from python/controllers/.

                  The server here is ltserv or ot_server. Everything is as of October 2026/OT 0.67.

                  What are the core classes?

                  Two listeners, one command table, and one object watching the game module's traffic. Click a box.

                  A server with the panel and the controller channel open is started like this:

                  ltserv <gamedir> worlds\multi\dm\dm_alley -web 8080 -primeclass AIMarine,AIAlien

                  -web 8080 serves the panel on http://127.0.0.1:8080/ and opens the controller channel on the next port, 8081. -control [PORT] opens the channel alone. Both bind to loopback unless -webbind-all is given.

                  When does a command run?

                  Inside the game loop, between two world updates. The control plane has no thread. Every socket is non-blocking and polled once per server frame, and a command line is parsed, executed and answered in the same call. At the default 100 Hz one round trip costs about 10 ms, and ten separate calls in a tick cost ten frames.

                    What is on the wire?

                    One JSON document per line, both ways, over TCP. The framing is a newline and there is no length prefix, so a session can be read and typed with nc. Nothing in the protocol is specific to Python. Pick a message.

                    Who may write?
                    Reading
                    Open to every peer able to reach the port. Every command in the table is marked read or write, and a caller without write rights gets the read ones.
                    Writing
                    Needs the token given with -webtoken, sent in hello by a controller and as ?token=, X-Token or a bearer header by the panel. With no token set, the panel lets a loopback peer write.
                    A wrong token
                    Does not close the connection. The controller is connected read-only, every write answers "changes the server and this connection is read-only", and the hello reply says so in write and token_accepted. A first controller with a mistyped token looks alive and does nothing.
                    Read-only server
                    -controlro refuses every write, from the panel and from every controller.
                    No token
                    With no token set, a controller may write only when it connects from the same machine. A server started with -webbind-all and no token gives controllers on other machines read access and nothing more.
                    What can a controller ask and do?
                    71 commands in one table, kCommands in runtime/control/controlapi.cpp. Each is also reachable over HTTP as /api/<command>. The help command returns the table from the running server and is the authority when this page grows old. Pick a group.
                    R is a read, W is a write. A position is [x, y, z] in world units with Y up; a standing marine is about 68 tall. Angles are radians.
                    What does the server tell a controller?
                    Events. A controller names the event types it wants in hello, and the subscription starts at the newest event, so a director connecting an hour into a match is not handed an hour of kills. Each event carries a sequence number seq and the game time t in seconds, and t restarts on every level.
                    The game module is a closed binary and offers no hooks. Every event above is decoded from messages the module sends to clients or receives from them, at three points in the engine. A bot dying is therefore not a kill event: the module tells clients about player kills only, and a dead bot shows as a body missing from bots.list.
                    Settings, buttons, pause and unload
                    Settings
                    A controller declares its settings in hello: a key, a label, a type and a default. The panel draws them and writes changes back. The types are string, number, bool, choice, text, point and button. The server interprets none of them. A number's range is advisory and the controller has to clamp.
                    Where the value lives
                    On the server, as text, keyed by controller name and setting key. A restarted controller therefore comes back with the operator's numbers and not with the defaults compiled into it. The server configuration file writes into the same store, and this is how a rotation gives a director six aliens on one level and twenty on the next.
                    A point
                    A place in the level held as text, "x z" or "x y z". The panel has a "pick on map" button for it and draws every declared point as a pin on the floor plan.
                    A button
                    A one-shot action. Nothing is stored, because a remembered press would fire again at the next hello with no operator looking. The controller receives a press event with the key.
                    Pause
                    A paused controller keeps receiving events and may read. Its ticks stop, its buttons are ignored, and the server refuses its writes. Pausing means "stop acting", and a controller unable to see the server could not notice being turned back on.
                    Unload
                    The panel asks the controller to leave. The socket stays open for a few frames so the controller can remove what it made. Nothing else will: the server keeps no list of who spawned what.
                    A level change
                    Controllers stay connected and receive world_loaded. Every object id held from the previous level is meaningless after it.
                    How do I write one?
                    In Python, with the opentalon package under python/. It needs nothing outside the standard library. A controller is a class deriving from Controller, one per file. This one greets players:
                    from opentalon import Controller, Setting

class Greeter(Controller):
    name = "greeter"
    settings = [Setting.text("greeting", "Greeting", "welcome")]

    def on_player_join(self, ev):
        self.api.say("%s, %s" % (self["greeting"], ev.get("name")))
                    The base class works the subscription out from the on_ methods a controller defines, declares the settings in hello, keeps self["key"] equal to the value on the server, and calls on_tick every tick_interval seconds (half a second by default). self.api is the client, with one method per command. Click a hook.
                    There are four ways to start it.
                    By hand
                    python3 -m opentalon.host controllers/greeter.py --port 8081 --token T, run from python/. The -m form matters, since it puts the directory on the import path. --set key=value overrides a setting before connecting.
                    From the panel
                    Every .py file in the controller directory is listed with a load button, and the button runs the command above. A file whose name begins with an underscore is a helper module and is not listed. Two comment lines at the top, # title: and # description:, name it in the list before it has ever run.
                    From a run script
                    scripts/servrun.sh --director and its neighbours start the server and the controllers together and keep each controller's output in a file. We prefer this for a measured run.
                    From the configuration file
                    A [Shared/controller:NAME] or [level/controller:NAME] block makes the server start and stop the controller as levels change, and every other key in the block is a setting for it.
                    The host reconnects if the server is not up yet, and gives up 20 seconds after losing a server it was connected to. An exception in a hook does not kill the controller. The last three lines of the traceback go to the controller's log in the panel, which is the place to look when a controller is silent.
                    Players can talk to a controller
                    A player typing <server> sentry install in chat is not chatting. The 2001 client strips the prefix and sends the rest to the server alone, and no other player sees it. The game module answers a few such verbs and ignores the rest. A controller can claim a verb with chat.claim. From then on every use of it arrives as a server_command event with the client, the verb and the arguments, the module never sees it, and the controller answers the one player privately with chat.tell.
                    No client code is involved, so this works with the retail game as shipped. In Python, CommandController turns each claimed verb into a cmd_<verb>(self, ev, args) method. Claims die with the connection, so a controller claims in on_load, which runs again after every reconnect.

                        Compatibility with the 2001 binaries
                        OpenTalon started as a reconstruction of LithTech Talon, the engine Monolith shipped Aliens versus Predator 2 on, and for most of its life it was developed by swapping one retail module at a time for OpenTalon's and checking that the game did not notice. That path is still in the tree as the 32-bit Windows build. We keep it as a reference: when the question is what the original does in some situation, we run the original and look.
                        Everything on this tab but its last section concerns that 32-bit build only. On 64-bit Linux and Windows no retail binary can be loaded, obviously. The last section is for authors of mods: it describes how a cshell.dll and an object.lto built for the 2001 engine are rebuilt for the 64-bit hosts.
                        What Monolith shipped
                        Four modules and two executables. The joints between them are the same ones shown on the Architecture tab. We kept them on purpose, so that either side of each joint can be the original.

                        Why is this hard at all?
                        Because the modules talk through C++ objects, with no C API in between. The slot a virtual method occupies and the byte offset of every member were fixed when Visual C++ 6 compiled the game in 2001. We compile with GCC, which follows a different C++ ABI, and the two disagree in three places. Two of them decide where a function is. The third decides how its arguments are passed, and we found that one from a page fault two years after the other two.
                        1. A virtual destructor is one slot
                        MSVC
                        1. 0 deleting destructor
                        2. 1 EngineMessageFn
                        3. 2 ObjectMessageFn
                        GCC, Clang
                        1. 0 complete destructor
                        2. 1 deleting destructor
                        3. 2 EngineMessageFn
                        4. 3 ObjectMessageFn
                        A plain virtual ~X() in a header would push every method below it down by one. The macro LT_MSVC_VDTOR_SLOT() stands in for the declaration in eight interfaces.
                        2. Overloads come out in reverse
                        MSVC
                        1. 104 GetObjectName(h, buf, n)
                        2. 105 GetObjectName(h)
                        GCC, Clang
                        1. 104 GetObjectName(h)
                        2. 105 GetObjectName(h, buf, n)
                        Virtual functions with the same name go into the table last-declared-first under MSVC. There are three such pairs in the whole interface set, and each is now written in the order the table wants.
                        3. A class passed by value
                        MSVC
                        1. pushes all 16 bytes
                        2. callee pops 36
                        GCC, Clang
                        1. pushes a 4-byte pointer
                        2. callee pops 24
                        LTRotation had a hand-written copy constructor, which was enough for GCC to pass it by hidden reference. Every moving door left 12 bytes on the game module's stack and returned into garbage. The constructor is now = default.
                        tests/test_abi holds 331 assertions on slots and offsets and runs in all five builds without game data. As a second opinion, Clang in MSVC-compatible mode computes the same tables from Monolith's unmodified headers, and all 122 slots we measured by hand agree with it.
                        Two C runtimes in one process
                        The retail modules carry a statically linked Visual C++ 6 runtime, and OpenTalon's link the UCRT. Two runtimes mean two heaps. A pointer allocated on one and freed on the other corrupts something, and does so long after the offending call. We audited every interface before the first swap, and nothing crosses. Only the life of a game object looks like it does.
                        The memory belongs to the engine from start to end; the module only constructs an object in it. Everything else the two exchange is either a caller-owned buffer with a length, or a handle the engine both hands out and takes back.
                        Which module gets loaded?
                        Game modules come out of the archive stack, as they always did, and the last one mounted wins. What we added is a check before loading. A module must be in the host's image format, and if it is an OpenTalon module, it must carry the ABI number this engine was built with.
                        A 64-bit host therefore skips the retail 32-bit modules at the first check and takes OpenTalon's from bin/opentalon.rez. A mod shipping a module in an archive mounted later overrides OpenTalon's, as a mod overrode Monolith's.
                        How is an existing mod converted?
                        A mod for Aliens versus Predator 2 is, as a rule, Monolith's SDK game source with changes, compiled by Visual C++ 6 into a 32-bit cshell.dll and object.lto. The 32-bit Windows build of OpenTalon loads those two files as they are. The 64-bit hosts skip them at the image-format check, so for Linux and 64-bit Windows the mod has to be compiled again.
                        The SDK source does not need porting a second time. The directory game/ is that source, already made to compile for 64-bit Linux and Windows, with the Master Server Patch protocol built in. A conversion therefore consists of moving the mod's changes onto that tree and repairing what the changes themselves assume about a 32-bit Windows machine.
                        1. Obtain the tree and build it unchanged
                        The game tree alone is exported with scripts/mkrepo.py PATH EXPORT_OT=False EXPORT_GAME=True. It is built as its README describes:
                        cmake -B build
cmake --build build -j
                        The result in build/bin/ is object.lto, cshell.dll, msp/cshell.dll (the shell for a Master Server Patch install) and opentalon.rez holding all three. The file names are the original ones on every platform; on Linux they are ELF shared objects under those names. A clean build before any change separates toolchain trouble from porting trouble.
                        2. Isolate the changes of the mod
                        The mod source is compared with the SDK source it started from, which gives the list of changed and added files. The SDK directories map onto the tree as follows.
                        SDKTreeBuilt into
                        ObjectDLL/game/objectdll/object.lto
                        ClientShellDLL/game/clientshell/cshell.dll
                        Shared/game/shared/both, compiled twice
                        ClientRes/game/clientres/the string table
                        ServerRes/game/serverres/the server's strings
                        File names in the tree are lower case, line endings are LF, the encoding is UTF-8, and #include lines use forward slashes. Linux file systems distinguish case, so an added file follows the same convention.
                        3. Apply them and add new files to the build
                        Changes go into the matching files. Lines the port touched carry an [OpenTalon] comment quoting the original, which shows where the tree already departs from the SDK. Source files are listed by name in game/CMakeLists.txt, in the order of the original project files. A new file is appended to the list of its module. Static objects are constructed in list order, as they were under Visual C++, so the position matters for code depending on another file's globals.
                        4. Compile, and repair what the compiler and the table point at
                        The tree builds with zero warnings, so every diagnostic after step 3 belongs to the mod. Most of the work is in the following patterns.

                        5. Strings and other resources
                        The client reads cres.dll out of the archives as data, on every platform. A mod's cres.dll therefore works as shipped, with its strings and cursors. Models, textures, sounds, levels and attribute files are data as well and need no conversion.
                        6. Pack the modules
                        A module is filed in an archive under game/<platform>/ with its original name. One archive can carry several platforms, and each host takes the entry named for its platform. The platform names are linux-x64, windows-x64 and windows-x86.
                        build/bin/mkrez mymod.rez \
    game/linux-x64/object.lto=build/bin/object.lto \
    game/linux-x64/cshell.dll=build/bin/cshell.dll \
    game/linux-x64/msp/cshell.dll=build/bin/msp/cshell.dll \
    game/windows-x64/object.lto=build-win64/bin/object.lto \
    game/windows-x64/cshell.dll=build-win64/bin/cshell.dll \
    game/windows-x64/msp/cshell.dll=build-win64/bin/msp/cshell.dll
                        The mod's data can go into the same archive or stay in the mod's existing ones.
                        7. Mount it last and read the log
                        The archive is named after the others, opentalon -rez mymod.rez or a -rez entry at the end of the install's avp2cmds.txt. The last mounted candidate wins, so the mod's modules replace those in opentalon.rez. At start the host prints one line per candidate, saying which was skipped and why and which was taken and from where. A module built against another version of the module interface is refused by name with both version numbers; rebuilding against the current tree resolves it.
                        Three checks are worth making before release: a single-player level loads and saves, a dedicated server and a client built from the same tree play a level change together, and a save written on Linux loads on Windows. Server and client of a mod must come from the same source, as before.
