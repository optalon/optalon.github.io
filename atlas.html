OpenTalon ABI Atlas

LithTech Talon consists of four modules connected only through C++ objects. This page maps those modules, the libraries OpenTalon builds them from, and each boundary at which one binary calls into another. The numbers are taken from docs/ARCHITECTURE.md, ABI.md, RENDERER.md and GAMEMODULES.md and were measured against the retail binaries.

This view shows the layouts of the 64-bit builds for Linux and Windows. The legacy view adds the 2001 binaries, their 32-bit layouts and the compiler rules needed to match them.

Plate 1

Which modules did Monolith ship?

Each module exports a few C functions and returns a vtable through them. These exports are everything the linker sees of a module. AVP2Serv.exe is a second host for server.dll and has no client, so the server can be tested alone.

Plate 2

How is OpenTalon layered?

The retail DLLs became static libraries under runtime/. The client engine and the server engine do not depend on each other. Both are linked by lt_listen alone, which single player and LAN hosting use.

Plate 3

Where do the modules meet?

There are four binary interfaces and one wire protocol; we call each of the five a seam. A binary seam is used in both directions: the outer module calls the engine through one interface and the engine calls back through another. A retail binary and OpenTalon's rebuild are interchangeable in the outer boxes.On the 64-bit hosts the outer boxes hold OpenTalon's modules. A retail binary can take their place in the 32-bit Windows build only.

Plate 4

What does an ILTServer* point at?

The interface is an object with a vtable and, after it, a block of plain function pointers. The game therefore reaches the engine in two ways. Visual C++ 6 fixed the slot of each method and the byte offset of each member when it compiled the retail modules.The slot numbers are those of the 2001 interface in every build. The byte offsets follow the pointer size.

Plate 5

Where do MSVC and the Itanium ABI disagree?

The 32-bit build is compiled with GCC and has to reproduce the layout of Visual C++ 6. We found three differences. Two of them decide the slot of a function. The third decides how arguments are passed; it was found through a page fault.

1. A virtual destructor takes one slot

MSVC
  1. 0 vector deleting dtor
  2. 1 EngineMessageFn
  3. 2 ObjectMessageFn
Itanium
  1. 0 complete dtor
  2. 1 deleting dtor
  3. 2 EngineMessageFn
  4. 3 ObjectMessageFn

The retail vtable of Light has three entries, and the destruct thunk of every class calls slot 0 with an nFlags argument.

LT_MSVC_VDTOR_SLOT() in sdk/inc/ltabi.h replaces the destructor declaration in eight interfaces.

2. Overloads of one name are emitted in reverse

MSVC
  1. 104 GetObjectName(h, buf, n)
  2. 105 GetObjectName(h)
Itanium
  1. 104 GetObjectName(h)
  2. 105 GetObjectName(h, buf, n)

Monolith declared the one-argument form first. The retail module calls slot 104 with three arguments and slot 105 with one.

There are three such pairs. Each is declared in vtable order, with a comment at the site.

3. A class passed by value

MSVC
  1. pushes LTRotation's 16 bytes
  2. callee: ret 0x24
Itanium
  1. pushes one 4-byte pointer
  2. callee: ret 0x18

A user-written copy constructor made LTRotation non-trivial for the purposes of a call. Each frame of a moving door left 12 bytes of the module's stack unpopped, until Door::MoveTo returned to a garbage address.

The constructor is now = default. scripts/abiargs.py derives the passing convention of every class type in sdk/inc.

Plate 6

Which side frees the memory?

MinGW links the UCRT, while the retail modules carry a static Visual C++ 6 runtime. A pointer allocated on one side and freed on the other corrupts a heap, and the fault shows long after the call. A game object appears to break this rule and does follow it, as the figure shows.

On 64-bit Windows each game module links its C runtime statically, so the engine and a module have separate heaps. On Linux they share one. On every platform the code frees memory on the side that allocated it. A game object appears to break this rule and does follow it, as the figure shows.

Plate 7

What does a renderer share with the engine?

The render interface is one struct filled in by both sides. The engine writes 15 callbacks at the front and RenderDLLSetup writes 38 function pointers further in. The built-in talon.ren is set up through the same call, so the two renderers can be compared with nothing else changed.

Plate 8

Which module gets loaded?

The MSVC layout matters only in a build able to load a retail binary. Game modules come out of the archive stack as they did in 2001. The engine now checks a candidate before loading it.
